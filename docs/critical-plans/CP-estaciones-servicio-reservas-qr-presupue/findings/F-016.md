# F-016 — Checkout deja orden, pago y reserva tras fallo de stock

- **Scenario:** Si la reserva de stock falla después de crear orden, vincular booking y pago pendiente, checkout responde error pero deja esos registros y bloquea el intervalo.
- **Proposed fix:** Incluir stock y fallos posteriores en una compensación completa, o no finalizar orden/pago/reserva hasta lograr todas las operaciones.
- **Resolution:** Checkout principal y checkout WhatsApp difieren promociones/`order.created` hasta reservar stock y fallan de forma cerrada ante cualquier error de reserva. La ruta principal usa `lockOrderLifecycle`, compartido con webhooks: si el pago u orden ya se liquidó, conserva orden y stock para conciliación; si no, cancela pago no terminal y orden antes de liberar reservas parciales y citas. WhatsApp cancela orden y reservas parciales. Si una compensación no se confirma, ambas rutas crean una notificación persistida `checkout_reconciliation_required` con ID/número de orden y motivo; un fallo al crear la alerta queda en logs y no reemplaza el error original del checkout. La migración aditiva para `checkout_reconciliation_required` se aplicó en el clon de base de datos de pruebas y la suite de idempotencia/concurrencia de checkout pasó 5/5.
