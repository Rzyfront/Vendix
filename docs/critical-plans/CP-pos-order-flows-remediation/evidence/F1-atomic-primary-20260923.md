# F.1 — reemplazo de dirección predeterminada atómico

El aislamiento por `store_id+user_id` de `F1-primary-isolation.md` evitaba desmarcar a *otros* clientes, pero seguía desmarcando la dirección predeterminada anterior **antes** de crear/actualizar la nueva. Un fallo de la segunda escritura dejaba al cliente sin predeterminada. Se añadieron dos pruebas red-before-green: `create` fallido y `update` fallido. Antes del arreglo ambas dejaban `is_primary=false` en la fila anterior; tras mover las dos escrituras a una misma transacción Prisma, ambas preservan el estado previo. Suite focalizada de tienda **7/7** verde (`/tmp/f1-atomic-red.log`, `/tmp/f1-atomic-green.log`).

La transacción usa el cliente Prisma crudo; por eso el `updateMany` de defaults conserva filtros explícitos `store_id` y `user_id`, y el `update` de la dirección destino incluye `id` **y** `store_id`. El alta también escribe `store_id` desde el contexto. Ninguna dirección de otra tienda puede entrar por el ID de un formulario. No se creó migración ni se alteraron direcciones históricas.

Como `addresses` no tiene índice único parcial para «una primaria por cliente», la transacción toma además `pg_advisory_xact_lock(hashtext('address_primary:<store>:<user>'))` antes del unset. Prueba focalizada roja antes del lock y **7/7** verde después. Dos POST simultáneos reales para el cliente #151 crearon #536 y #537 (ambos 201), pero SQL halló **una sola** primaria (#537); ambas filas QA se eliminaron con 204, dejando el conteo de tienda otra vez en 11 y cero QA remanentes. Cuerpos `/tmp/f1-concurrent-{A,B}.json` y estados homónimos.

API local tienda #10 con owner existente (sin nuevo login): `PATCH /store/addresses/484 {is_primary:true}` **200**, restauración a false **200**; `POST /store/addresses` para cliente #151 con primary creó dirección QA #535 **201**, y `DELETE #535` **204**. Conteo SQL de predeterminadas tienda **11 antes / 11 después**; #484 y #529 terminaron en false, #535 eliminada. Backend watch `API_READY`, `/health` 200. Evidencia cruda `/tmp/f1-atomic-{before,after}.txt`, `/tmp/f1-lock-*` y `/tmp/f1-atomic-*.json`. La prueba del rollback ante fallo pertenece al spec (no se indujo un fallo de base sobre datos reales).

**No cubierto aquí:** ocho direcciones huérfanas `is_primary=true` preexistentes de tiendas, la eventual adopción de huérfana mediante `UpdateAddressDto.customer_id` (hoy se ignora), y la decisión ADR-05/F.2. No se hace backfill ni se declara F.1 completo por esos huecos.
