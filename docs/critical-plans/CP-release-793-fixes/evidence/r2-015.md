# R.2 — F-015: parseInt sobre ids tipados string

- **Verdict:** CONFIRMADO (minor, frágil; tolerado por el backend)
- **Fecha:** 2026-09-11 · Rama: `develop` (solo lectura; sin cambios de código)

## Comando

```bash
sed -n '175,200p' apps/frontend/src/app/public/ecommerce/pages/pqr/pqr-submit.component.ts
rg -n "id:|organizationId" apps/frontend/src/app/core/models/tenant-config.interface.ts
sed -n '76,88p' apps/backend/src/domains/support/pqr/dto/create-pqr-public.dto.ts
sed -n '125,137p' apps/backend/src/domains/support/pqr/pqr.service.ts
```

## Salida

1. `pqr-submit.component.ts:181-185`: `parseInt(currentOrg.id.toString(), 10)`
   y `parseInt(currentStore.organizationId.toString(), 10)` sobre
   `OrganizationConfig.id: string` y `StoreConfig.organizationId: string`
   (`tenant-config.interface.ts:55,83,87`). `parseInt` hace parse parcial
   (`"12ab"→12`) y `NaN` ante no-numérico; `NaN` serializa a `null` en JSON.
2. Backend tolera: `organization_id?` y `store_id?` son `@IsOptional() @IsInt()`
   (`create-pqr-public.dto.ts:76-88`; `@IsOptional` salta `null/undefined`) y
   el servicio resuelve la org desde `store_id` cuando falta `organization_id`
   (hunk nuevo del diff en `pqr.service.ts:128-136`). No rompe, pero el
   `"12ab"→12` podría atribuir el ticket a la org equivocada.

## Veredicto

CONFIRMADO como fragilidad menor sin ruptura actual. Fix según directiva:
`Number()` + guard `Number.isInteger` antes de poblar el DTO.
