# The Bundle Format

Load this when creating, editing, or linting a critical-plan bundle (`docs/critical-plans/CP-<slug>/`): the file layout, ID patterns, the per-fragment frontmatter and body schema, the token/byte budgets, and the read/write protocol each actor uses to load only its own fragment. It replaces the v1.1 **Required Critical Plan Format** section. This file is the canonical contract; `assets/templates/*.md` and `assets/cp-*.sh` implement it and are not restated here.

## Bundle layout

```
docs/critical-plans/CP-<slug>/
├── PLAN.md                      # hub
├── adr/ADR-01-<slug>.md         # one decision per file
├── registry/fb.md               # Frontend↔Backend Contract Registry
├── registry/db.md               # Database Contract Registry
├── registry/err.md              # Error Code Registry
├── steps/A.1-<slug>.md          # one step per file (12 fields)
├── findings/F-001.md            # one finding per file
├── log/execution.md             # Execution Log (append-only)
├── log/convergence.md           # Perspective Audit Matrix + Convergence Loop Log
├── inventory/files.md           # Critical Files
├── inventory/assets.md          # Reusable Assets
└── evidence/.gitkeep            # verification outputs (never /tmp)
```

`docs/` is gitignored in this repo: a bundle reaches the team only with `git add -f docs/critical-plans/CP-<slug>` (the `docs/evidence/` precedent). Add it in the same PR as the code it governs.

ID patterns (regex): step `^[A-Z]\.[0-9]+$` (`A.1`, `B.12`) · ADR `^ADR-[0-9]{2}$` · finding `^F-[0-9]{3}$` · registry row `^FB-[0-9]{2}$` / `^DB-[0-9]{2}$` / `^ERR-[0-9]{2}$`. Filenames: step/ADR = `<id>-<slug>.md` (`A.1-crear-roles.md`, `ADR-01-variant-propagation.md`); finding = `<id>.md` exact.

## v1.1 → v2.0 section map

The old single-file format had 22 mandatory sections; this table is where each one now lives.

| v1.1 section | v2.0 location |
|---|---|
| Plan Identity | `PLAN.md` frontmatter |
| Execution Ledger | `PLAN.md` § Execution Ledger (GENERATED by `cp-ledger.sh`) |
| Context · Criticality Justification · General Objective · Specific Objectives · Non-Goals · Approach Chosen · Alternatives Considered · Blast Radius · Data Integrity Plan · End-to-End Verification · Rollback Plan · Knowledge Gaps · Approval Request | `PLAN.md` (hand-written) |
| *(new)* Phases | `PLAN.md` § Phases — `Phase / Name / Goal` table, defines the letter, name and goal of each phase |
| *(new)* Fragment Index | `PLAN.md` § Fragment Index (GENERATED) |
| Architecture Decision Records | `adr/` |
| Critical Files | `inventory/files.md` |
| Reusable Assets | `inventory/assets.md` |
| Contract Inventory (3 registries) | `registry/fb.md`, `registry/db.md`, `registry/err.md` |
| Phases and Steps | `steps/` |
| Perspective Audit Matrix | `log/convergence.md` § Perspective Audit Matrix |
| Convergence Loop Log | `log/convergence.md` § Convergence Loop Log |
| Execution Log | `log/execution.md` |

## Frontmatter (all fragments)

- Line 1 is `---`; the block ends at the next `---` line.
- Each line is `key: value`. `key` = up to the first `:`; `value` = the rest, trimmed, no wrapping quotes.
- Allowed values: scalar (`A.1`, `2026-09-05`, `"text with: a colon"`) or an inline list `[a, b, c]` (may be `[]`). FORBIDDEN: nested maps, block lists (`- item`), multiline values.
- Reference parser (awk): read between the first and second `---`; `sub(/^[^:]+:[[:space:]]*/,"")`; strip `^"|"$`; for lists strip `[` `]`, split on `,`, trim each element. See `skills/skill-sync/assets/sync.sh:66-90`.
- The `# …` comments in the schemas below are documentation only. Never write them into a real fragment: the parser would read them as part of the value.

## Fragment types

### `PLAN.md` (hub)

```yaml
---
id: CP-<slug>
title: "<plan title>"
criticality: "<what breaks if this fails>"
owner: <name>
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: planning        # planning | approved | in-execution | converging | done
issue: none              # QUI-nnn | none
---
```

Sixteen mandatory H2 sections, in this exact order (an H2 line may carry a trailing `<!-- … -->` hint, as the template does; the tooling compares the heading text only):

1. `## Execution Ledger` — GENERATED block (see below) + a hand-written `**Handoff notes:**` line outside the markers.
2. `## Fragment Index` — GENERATED block (see below).
3. `## Context`
4. `## Criticality Justification`
5. `## General Objective`
6. `## Specific Objectives`
7. `## Non-Goals`
8. `## Phases` — table `| Phase | Name | Goal |`, one row per letter (`| A | Foundations | … |`).
9. `## Approach Chosen`
10. `## Alternatives Considered`
11. `## Blast Radius` — table `| Surface | What breaks if this plan is wrong | Who notices | Detection signal |`
12. `## Data Integrity Plan`
13. `## End-to-End Verification`
14. `## Rollback Plan` — table `| Phase | Trigger to roll back | Procedure | Data recoverable? | Who decides |`
15. `## Knowledge Gaps`
16. `## Approval Request` — the verbatim block:
    > This critical plan is ready for human review. Reply **"ejecuta"**, **"apruebo"**, or **"procede"** to start execution under `how-to-dev`, with the Living Document Protocol and the Convergence Loop in force. Reply with corrections to revise the plan in place.

**Generated content — `cp-ledger.sh` writes this, nobody edits it by hand:**

```markdown
<!-- ledger:start -->
_Generated by `cp-ledger.sh` on YYYY-MM-DD — do not edit by hand._

| Phase | Steps | Done | In progress | Blocked | Skipped | Status |
|-------|-------|------|-------------|---------|---------|--------|
| A — Foundations | 6 | 6 | 0 | 0 | 0 | ✅ Complete |
| B — Contracts | 9 | 4 | 1 | 1 | 0 | 🟡 In progress |

**Current position:** B.5 — <title>          ← first in-progress step; else first pending; else first blocked; else "All steps closed"
**Owner:** <hub owner> · **Last updated:** YYYY-MM-DD
**Open blockers:** B.6 — <title>              ← steps with status blocked, or "None"
**Open findings:** 2 blocker · 3 major · 1 minor · 0 note   ← open findings by severity
<!-- ledger:end -->
```

Per-phase `Status` rule: `✅ Complete` if `done + skipped == steps` and `steps > 0`; `⬜ Not started` if `done + in-progress + blocked + skipped == 0`; `🔴 Blocked` if `blocked > 0`; else `🟡 In progress`.

```markdown
<!-- index:start -->
### Steps
| Id | Title | Status | Contracts | Updated |
|----|-------|--------|-----------|---------|

### ADRs
| Id | Title | Status | Reversibility |
|----|-------|--------|---------------|

### Open findings
| Id | Severity | Step | Perspective | Round |
|----|----------|------|-------------|-------|
_Closed: N fixed · N accepted · N rejected_

### Registries
| Registry | Rows | Verified |
|----------|------|----------|
<!-- index:end -->
```

Both blocks are regenerated in full by `cp-ledger.sh` at the end of every session and after every step-status change — never hand-edit between the markers (see `references/convergence.md` for when a convergence round triggers this).

### `steps/<id>-<slug>.md`

```yaml
---
id: A.1
title: "<step title>"
phase: A
status: pending          # pending | in-progress | blocked | done | skipped
owner: none              # name | none
updated: YYYY-MM-DD
contracts: []            # [FB-01, DB-03, ERR-02]
adrs: []                 # [ADR-01]
skills: []               # [vendix-permissions, vendix-prisma-seed]
---
# A.1 — <title>

- **Skills:** …
- **Resources:** …
- **Business decision:** …
- **Why:** …
- **Output:** …
- **Contracts touched:** FB-01, DB-03 | none — <reason>
- **Data impact:** … | none — <reason>
- **Blast radius:** …
- **Rollback:** … | irreversible — see ADR-nn
- **Verification:**
  - <exact runnable command>
- **Acceptance checklist:**
  - [ ] <granular item ≤ 200 chars>
  - [ ] F-003 — <finding title> (major)
- **Status:** pending
```

The TWELVE labels, in this exact order and spelling, each a line starting with `- **<Label>:**`:
`Skills`, `Resources`, `Business decision`, `Why`, `Output`, `Contracts touched`, `Data impact`, `Blast radius`, `Rollback`, `Verification`, `Acceptance checklist`, `Status`.

- The first word of the `- **Status:**` line must match the frontmatter `status` (`pending` · `in-progress · <owner> · <date>` · `blocked — Blocker: <what/who>` · `done · <owner> · <date> · <evidence/...>` · `skipped — Descartado: <reason> · authorized by <name>`).
- Checkbox vocabulary: `[ ]` pending · `[~]` in progress · `[x]` done AND verified · `[!]` blocked · `[-]` deliberately skipped (with `Descartado:` and an authorizer).
- Finding checklist line — exact grammar: `- [<mark>] F-nnn — <title> (<blocker|major|minor|note>)`, optionally followed by ` → <evidence/...>`. A given `F-nnn` appears **at most once** in a step; closing it changes the mark on that SAME line — never a second line.
- Long rationale never goes in the checklist: it goes to the finding or an ADR.

### `adr/ADR-nn-<slug>.md`

```yaml
---
id: ADR-01
title: "<decision>"
status: proposed         # proposed | accepted | superseded
reversibility: costly    # trivial | costly | one-way
updated: YYYY-MM-DD
---
# ADR-01 — <decision>

- **Context:** …
- **Decision:** …
- **Consequences:** …
- **Reversibility:** trivial | costly | one-way door — <why>
- **Revisit if:** …
```

### `findings/F-nnn.md`

```yaml
---
id: F-001
round: 1
perspective: 3           # 1..13
severity: major          # blocker | major | minor | note
step: A.1                # owning step id | none
status: open             # open | fixed | accepted | rejected
accepted_by: none        # human name if status = accepted
location: "apps/backend/src/domains/x/y.service.ts:120"
updated: YYYY-MM-DD
---
# F-001 — <title>

- **Scenario:** <inputs → wrong outcome>
- **Proposed fix:** …
- **Resolution:** — (commit / evidence/... once closed)
```

Rule: `status: accepted` requires `accepted_by` ≠ `none`. A finding with `step` ≠ `none` and `status` ∈ {open, fixed} must be referenced exactly once in that step's checklist.

### Registries — `registry/{fb,db,err}.md`

No frontmatter. H1 title + one table. One row = one line ≤ 400 chars. `Status` is `[ ]` or `[x]`.

```markdown
# Frontend↔Backend Contract Registry
| Id | Method + route | Request DTO | Response shape | Frontend consumer | Change | Risk | Verification | Status |
|----|----------------|-------------|----------------|-------------------|--------|------|--------------|--------|
```

```markdown
# Database Contract Registry
| Id | Model / table | Columns | R/W | Tenant scoping | Migration | Consumers | Invariant | Verification | Status |
```

```markdown
# Error Code Registry
| Id | Code | HTTP | Emitted when | Frontend behavior | Message shown | Verification | Status |
```

### Logs

`log/execution.md` — no frontmatter, append-only, rows ≤ 300 chars; `Evidence` is an `evidence/...` path, a commit sha, or a PR URL. `/tmp/` is banned everywhere in the bundle.

```markdown
# Execution Log
| Date | Who | Step | Event | Evidence |
|------|-----|------|-------|----------|
```

`log/convergence.md` — two sections:

```markdown
# Convergence
## Perspective Audit Matrix
| # | Perspective | Round run | Findings (B/M/m/N) | Status |
|---|-------------|-----------|--------------------|--------|
| 1 | Architecture | — | 0/0/0/0 | pending |
… (13 rows; N/A requires a reason in Status)

## Convergence Loop Log
| Round | Date | Blockers | Majors | Minors | New steps filed | Findings | Outcome |
|-------|------|----------|--------|--------|-----------------|----------|---------|
```

Rows ≤ 300 chars; `Findings` lists the round's `F-nnn` ids (detail lives in `findings/`). Full rules and the closing-a-finding table: `references/convergence.md`.

### Inventories

`inventory/files.md`: `# Critical Files` + a list `- \`concrete/path.ts\` — role`. No wildcards.
`inventory/assets.md`: `# Reusable Assets` + a list `- \`path\` — what it provides`, or `none — <reason>`.

## Contract Discipline

This is the section the skill exists for. **A contract break is the failure mode critical work dies from**, because it passes every build, every type check and every unit test, and shows up in production as a blank screen, a wrong number, or a 500 with no explanation.

### Why a type check is not a contract verification

`tsc` proves the code agrees with the **declared** interface. It cannot prove the declared interface agrees with what the server **actually sends**. A frontend interface that says `total: number` compiles perfectly against a backend that sends `total: string` — and breaks at runtime on the first `.toFixed()`.

**A contract is verified only by comparing a live response against the declared shape.** Both sides. Every time.

### The four failure modes every contract check must rule out

| Failure mode | Symptom in production |
|--------------|-----------------------|
| **Field of more** — the client sends a field the server rejects | 400 with `forbidNonWhitelisted`, or a silently ignored value |
| **Field of less** — the client omits a field the server requires, or the server stops sending one the client reads | 400 on write; `undefined` propagating into the UI on read |
| **Type mismatch** — same field name, different type | `NaN`, `Invalid Date`, `[object Object]` rendered to the user |
| **Optionality mismatch** — required becomes optional or vice versa | Works for every existing row and breaks on the first new one |

### Registry rules

**Frontend↔Backend (`registry/fb.md`)**
- `Change` names the exact delta: `+ field`, `- field`, `field renamed a→b`, `field type number→string`, `field required→optional`, `none (regression check only)`.
- Endpoints the plan does not change but whose consumers it touches still get a row, marked `none (regression check only)`. A component refactor breaks contracts just as effectively as a DTO edit.
- `Verification` is a runnable command, not a description — the canonical form compares live keys against the declared interface, never just "check it returns 200".
- `Status` is ticked by a human after running the verification, not after reading the code.

**Database (`registry/db.md`)**
- **`Tenant scoping` is mandatory on every row.** Name the mechanism: scoped client, `withoutScope()` with an explicit filter, fiscal-entity scope, or relational scope. `withoutScope()` without a written justification is a `blocker` by definition.
- **`Invariant` is the property that must hold before and after.** A row without one is unverifiable; if "none", say why.
- Every row-mutating migration carries the `-- DATA IMPACT:` header and the checklist required by the global migration rules and `vendix-prisma-migrations` — a hard gate, not a suggestion.
- **Verification runs against a representative dataset**, never an empty local database. A migration that passes on zero rows has proven nothing.

**Error codes (`registry/err.md`)**
- **Every path that can throw has a row.** `throw new Error('...')` reaching a controller is a `blocker`: it becomes a raw 500 with no code the frontend can branch on.
- `Frontend behavior` is mandatory — an error code nobody handles is an unhandled error with extra steps.
- Codes come from the project's standardized catalog (see `vendix-error-handling`); inventing one inline without registering it is a format break.
- **Beware the 200-with-`success:false` shape.** A handler that catches its own exception and returns a success envelope produces a failure the frontend renders as data. Register which shape each path uses.

### Contract sweep gate

Before the plan can be declared done:

- [ ] Every row in `registry/fb.md` has `Status: [x]`, ticked after running its verification against a live server.
- [ ] Every row in `registry/db.md` has `Status: [x]`, ticked after running its invariant query on real data.
- [ ] Every row in `registry/err.md` has `Status: [x]`, ticked after provoking the error and observing the frontend.
- [ ] The row count in each registry equals the count of touched points found in Phase 2. A shrinking registry means something was dropped, not that the work got smaller.

## Living Document Protocol

### Checkbox vocabulary

| Marker | Meaning | Required companion |
|--------|---------|--------------------|
| `- [ ]` | Pending | — |
| `- [~]` | In progress | Owner + start date on the same line |
| `- [x]` | Done **and verified** | Evidence: command output, PR link, screenshot path |
| `- [!]` | Blocked | A `Blocker:` line stating what is blocking and who can unblock |
| `- [-]` | Deliberately skipped | A `Descartado:` line with the reason and **who authorized it** |

`- [x]` means verified, not written. Ticking a box because the code was typed is the most common way a critical plan becomes fiction.

### The Execution Ledger (`PLAN.md` § Execution Ledger)

Unlike v1.1, this table is **GENERATED by `cp-ledger.sh`**, run at the end of every session and after every step-status change — never edited by hand between `<!-- ledger:start -->` / `<!-- ledger:end -->`. `**Handoff notes:**` stays hand-written, outside the markers, and is not optional prose: half-finished branches, scratch scripts, credentials used, decisions taken verbally — whatever the next person needs and cannot derive from the file.

**Never delete a resolved blocker line.** Move it to `log/execution.md` with its resolution — the history of what blocked the work is evidence the next reader needs.

### The Execution Log (`log/execution.md`)

Appended, never rewritten. One row per meaningful event, ≤ 300 chars. Long detail (command output, diffs, screenshots) goes to `evidence/`, never `/tmp`.

| Date | Who | Step | Event | Evidence |
|------|-----|------|-------|----------|
| 2026-08-18 | rzy | B.4 | Contract sweep of 12 order endpoints completed; FB-07 mismatch found and fixed | `evidence/fb-07.txt` |

## Budgets

Tokens ≈ bytes / 4, measured with `wc -c`; `cp-lint.sh` FAILS on any excess.

| Artifact | Limit |
|---|---|
| `PLAN.md` (hub) | 8,000 tokens = **32,768 bytes** |
| `steps/*.md` | 2,500 tokens = **10,240 bytes** |
| `adr/*.md` | 1,500 tokens = **6,144 bytes** |
| `findings/*.md` | 800 tokens = **3,200 bytes** |
| registry row (`registry/*.md`) | **400 chars** |
| log row (`log/*.md`) | **300 chars** |
| checklist item (`- [.] …` line in a step) | **200 chars** |

A step that does not fit in 2.5k tokens is two steps.

## Read protocol

Every actor loads only its fragment via `cp-context.sh`, never the whole bundle.

| Actor | Loads | Command |
|---|---|---|
| Human / orchestrator, cold start | `PLAN.md` in full | `cp-context.sh <bundle> hub` |
| Executor of step X | step X + its registry rows + its ADRs | `cp-context.sh <bundle> step <X>` |
| Perspective agent n, on steps S1 S2 … | hub excerpt (Context, Specific Objectives, Blast Radius) + domain registry (perspective 3→fb, 4→db, 5→err; others: none) + steps S1, S2 … + the audit matrix | `cp-context.sh <bundle> perspective <n> <S1> <S2> …` |
| Contract sweep of one registry | that registry only | `cp-context.sh <bundle> sweep fb\|db\|err` |
| Convergence dedup | every finding regardless of status | `ls findings/` (directory listing, not `cp-context.sh`) |

## Write protocol

- A finding is a first-class record: `findings/F-nnn.md`. In its owning step it occupies exactly ONE checklist line: `- [ ] F-nnn — <title> (<severity>)`.
- Closing a finding flips the mark on that SAME line — never adds a second line.
- Long rationale goes to the finding (`Scenario` / `Proposed fix` / `Resolution`) or an ADR, never to a checklist item.
- Log rows ≤ 300 chars; details go to `evidence/`.
- The ledger and the Fragment Index are never written by hand — run `cp-ledger.sh`.
- Evidence always lives in `evidence/` inside the bundle, never `/tmp`.

## Field-by-Field Rigor

The six fields inherited from `how-to-plan` keep its rules unchanged. The six new fields have their own acceptance bar:

| Field | Acceptable | Rejected |
|-------|------------|----------|
| `Contracts touched` | `FB-03, FB-04, DB-07` — ids that exist in the registries | "the orders endpoints" |
| `Contracts touched` (none) | `none — this step only moves a component file` | (field omitted) |
| `Data impact` | "Writes ~4.200 rows in `inventory_movements`; reads all of `products` for the store" | "some database changes" |
| `Data impact` (none) | `none — read-only step` | (field omitted) |
| `Blast radius` | "If wrong, every POS sale in a restaurant store posts to the wrong PUC account, silently" | "could cause bugs" |
| `Rollback` | "`git revert <sha>`; the migration is additive, no data undo needed" | "revert if needed" |
| `Rollback` (irreversible) | "irreversible — a DIAN consecutive is burned; see ADR-3 for the mitigation" | "can't roll back" |
| `Acceptance checklist` | 4-12 granular `- [ ]` items, each independently tickable and verifiable | One item saying "step done" |
| `Status` | `done · rzy · 2026-08-18` | `done` |
